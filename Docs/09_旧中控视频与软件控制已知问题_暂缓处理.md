# 旧中控视频与软件控制已知问题（暂缓处理）

## 文档状态

- 记录日期：2026-08-24
- 对象：从 `CenterSystem.apk` 恢复的旧版 Android 平板中控 Unity 工程
- 当前决定：问题已经完成发送端静态审计并留档，暂缓整改；后续工作转入新版中控系统的需求与架构梳理。
- 使用原则：旧工程作为功能、界面和现场协议参考，不直接作为新版系统的架构基础。

## 已完成的相关基础整改

- Android 配置读取改为异步流程，移除初始化阶段的忙等待。
- TCP 控制器增加连接队列、串行发送、异常保护和诊断记录。
- UDP 客户端改善 Socket 与接收线程的启停、销毁和重复实例管理。
- 网络唤醒增加参数校验、重复发送和诊断记录。

上述整改主要针对通信基础设施和旧工程可运行性，不代表视频与软件控制业务逻辑已经完成整改。

## 已确认问题

### 1. 软件打开与关闭指令无法区分

`SoftController` 分别广播打开和关闭事件，但 `UDPClient.OpenSoft` 与 `UDPClient.CloseSoft` 最终都原样发送同一个 `softName`。如果接收端没有额外的状态切换约定，无法判断本次操作是打开还是关闭。

相关代码：

- `Assets/Scripts/Assembly-CSharp/SoftController.cs`
- `Assets/Scripts/Assembly-CSharp/UDPClient.cs`

### 2. 旧视频控制面板存在事件参数类型错误

`ControlVideoPanel` 的播放和快退操作按无参数事件广播，而 UDP 监听器要求字符串参数。事件中心会捕获委托转换异常，因此对应按钮可能没有有效指令发出。

同一播放开关还注册了两次监听，关闭时可能重复发送暂停指令。

相关代码：

- `Assets/Scripts/Assembly-CSharp/ControlVideoPanel.cs`
- `Assets/Scripts/Assembly-CSharp/EventCenter.cs`
- `Assets/Scripts/Assembly-CSharp/UDPClient.cs`

### 3. 自定义端口配置未真正生效

新增视频控制项时，界面虽然提供端口输入，但保存调用固定传入 `8888`；打开控制面板时又通过 `InitSocket(ip)` 使用 UDP 默认端口 `7002`。现场填写的端口无法贯穿到实际连接。

相关代码：

- `Assets/Scripts/Assembly-CSharp/AddSoftWareDetail.cs`
- `Assets/Scripts/Assembly-CSharp/UDPClient.cs`

### 4. UDP目标采用全局活动实例，存在目标覆盖风险

动态创建视频或软件控制面板时会添加新的 `UDPClient`，并把全局活动目标切换到新 IP 和端口。快速切换模块、面板延迟创建或多个控制面板并存时，旧目标可能被覆盖，导致指令发错设备或被非活动实例忽略。

相关代码：

- `Assets/Scripts/Assembly-CSharp/SoftWareManager.cs`
- `Assets/Scripts/Assembly-CSharp/UDPClient.cs`
- `Assets/Scripts/Assembly-CSharp/UDPClient2.cs`

### 5. UDP没有业务级确认与重试

当前发送成功仅表示本机 Socket 已执行 `SendTo`，没有指令编号、接收确认、执行结果、超时重试和幂等控制。界面完成点击不等于大屏客户端已经执行。

这也是旧系统出现“点击后偶发没有反应，重启软件后恢复”的可能原因之一。

### 6. 双客户端视频控制不具备一致性保障

双屏场景分别向 `UDPClient` 和 `UDPClient2` 广播指令，没有统一事务、时间戳、播放位置校准或两端确认。可能出现单屏执行、启动时间不一致或播放进度逐渐偏移。

相关代码：

- `Assets/Scripts/Assembly-CSharp/VideoPlayControl.cs`
- `Assets/Scripts/Assembly-CSharp/UDPClient.cs`
- `Assets/Scripts/Assembly-CSharp/UDPClient2.cs`

### 7. 风效开启码与关闭码完全相同

静态比对确认 `FengOpenCode` 与 `FengCloseCode` 内容完全一致，因此风效关闭操作无法可靠表达不同动作。最终正确指令仍需结合现场红外设备协议确认。

相关代码：

- `Assets/Scripts/Assembly-CSharp/VideoPlayControl.cs`

### 8. 局域网控制协议缺少安全保护

视频和软件指令使用明文 UDP 字符串，没有身份认证、签名、防重放和来源校验。若控制网络中存在非受信设备，理论上可以伪造控制报文。接收端源码尚未取得，暂时不能完成端到端安全确认。

### 9. 恢复源码包含硬编码数据库连接信息

恢复出的 `SqlManager.cs` 原本包含公网数据库地址和明文账号密码。为避免敏感信息进入 GitHub，归档提交已将其替换为环境变量：

- `TG_CONTROL_SQL_CONNECTION`
- `TG_CONTROL_SQL_EDITOR_CONNECTION`

该脱敏仅用于安全归档，不代表旧版登录和数据库架构已经完成整改。原凭证如果仍在使用，应立即在数据库侧轮换，不能继续依赖旧值。

## 尚未完成的审计范围

- 大屏 Unity 定制播放客户端的接收、解析和执行代码。
- 被控 Windows 软件的启动、关闭和进程守护实现。
- 视频播放完成、异常退出、断网重连和状态恢复逻辑。
- 双屏帧级或时间轴级同步机制。
- 现场真实 IP、端口、协议返回值及红外码验证。

## 新版系统设计时的约束

新版中控应把旧工程的上述做法视为风险样本，至少采用：

- 每台设备独立连接与状态，不使用可被界面切换覆盖的全局目标。
- 明确区分 `OpenSoftware`、`CloseSoftware`、`Play`、`Pause`、`Stop` 等动作。
- 指令携带唯一编号、目标设备、时间戳和期望状态。
- 接收端返回已接收、执行成功或失败以及当前实际状态。
- 超时重试必须具备幂等机制，避免重复执行副作用。
- 双屏和语音联动由统一流程编排器下发时间轴或同步起播时间。
- 控制网络至少增加来源白名单和消息认证，并保留完整操作日志。
