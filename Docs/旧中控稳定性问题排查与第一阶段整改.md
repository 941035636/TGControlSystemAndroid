# 旧中控稳定性问题排查与第一阶段整改

> 日期：2026-08-24  
> 目标平台：Android 平板  
> Unity：2020.3.35f1c2  
> 原则：保留现有 UI、设备映射和报文兼容性，优先解决偶发失效与重启后恢复问题。

## 1. 本阶段目标

在不改变客户现有操作习惯的前提下：

1. 修复单设备开关偶发无效。
2. 修复一键全开/全关高频漏执行。
3. 降低重复 Socket、接收线程和全局事件串线造成的资源占用。
4. 提高网络唤醒从 Android Wi-Fi 平板直发的成功率。
5. 审计其他会影响长期运行稳定性的代码问题。

## 2. 客户现象与代码根因对应

| 客户现象 | 已确认的代码根因 | 判断 |
|---|---|---|
| 点开关偶发无效 | TCP 连接未完成时发送函数直接返回，指令被静默丢弃 | 确定 |
| 重启软件后又能控制 | 重启会清掉旧 Socket 和线程，重新建立连接 | 与现象高度一致 |
| 一键全开/全关最明显 | 一键功能只把 Toggle 设为 `true`；原来已经为 `true` 的 Toggle 不触发事件 | 确定 |
| 红外偶发无效 | `TcpControl90.Connect()` 创建 Socket 后立即再次判断未连接、关闭并重建，干扰异步连接 | 确定 |
| 运行时间越长越不稳定 | 动态增加多个 `UDPClient`，全部监听同一组全局事件并创建永久接收线程 | 确定 |
| 切换软件/控制页后异常增加 | UDP 初始化未先释放旧 Socket/线程，事件会同时命中多个实例 | 确定 |
| Wi-Fi 平板发 WOL 不成功，有线服务端成功 | 旧代码只向 `255.255.255.255:50000` 发一次；Wi-Fi AP 很可能不转发无线到有线的二层广播 | 高概率，需现场抓包确认 |

## 3. TCP 原代码的关键缺陷

### 3.1 固定等待 1 秒并不代表连接成功

原业务流程：

```text
Connect()
  ↓
固定等待 1 秒
  ↓
SendSingleCode()
  ↓
如果 socket == null 或 socket.Connected == false，直接结束
```

Wi-Fi 抖动、设备刚上电、ARP 解析或 TCP 重传超过 1 秒时，命令会丢失，UI 又没有失败提示。

### 3.2 连接中重复覆盖 Socket

`Socket.Connected` 在异步连接完成前必然为 `false`。用户再次点击时，原代码会重新 `new Socket()` 并覆盖字段；旧异步回调仍可能返回，但发送函数使用的是新字段，导致连接与发送对象错位。

### 3.3 TCP90 存在一次调用内的自我干扰

原 `TcpControl90.Connect()` 中有两个连续的 `if (!socket.Connected)`。第一个开始异步连接，第二个立即执行并关闭刚创建的 Socket，再发起第二次连接。这是红外控制不稳定的直接代码漏洞。

### 3.4 没有发送队列和完整发送处理

- 多个 Toggle 协程可以同时调用同一 Socket。
- `BeginSend` 没有保证处理“只发送了部分字节”的情况。
- 发送异常回调中直接 `throw`，可能造成线程异常。
- 断线后不自动恢复当前命令。

## 4. 一键全开/全关缺陷

原代码核心是：

```csharp
togarrEquip[i].isOn = true;
```

Unity Toggle 只有状态发生变化时才触发 `onValueChanged`。因此：

- UI 显示“开”，设备实际没开时，再执行一键全开不会补发。
- 上一次命令丢失后，UI 状态和设备状态永久不一致。
- 再次打开软件后 Toggle 恢复初始状态，命令才重新触发，形成“重启后就好了”的假象。

## 5. UDP 资源占用与串线

旧架构会在打开视频、软件或双客户端控制面板时动态执行：

```csharp
gameObject.AddComponent<UDPClient>();
EventCenter.BroadCast(Eventdefine.InitSocketIP_port, ip, port);
```

但 `InitSocketIP_port` 是全局事件，已有的所有 `UDPClient` 都会收到。结果包括：

- 多个 UDP 实例被同时改到同一目标地址。
- 同一命令可能重复发送。
- 每次初始化都会新建阻塞式接收线程。
- 旧线程使用 `Thread.Abort` 强制退出。
- 页面切换后容易积累 Socket、线程和事件监听。

这属于真实的长期运行稳定性问题。

## 6. 已实施的第一阶段修复

### 6.1 新增统一可靠 TCP 传输层

新增 `ReliableTcpControlBase.cs`，原 `TcpControl*` 保留类名和 Unity 脚本 GUID，只替换内部实现。

改进内容：

- 同一控制器只允许一个正在建立的连接。
- 连接期间收到的命令进入队列，不再丢弃。
- 连接超时自动关闭并重连。
- 发送失败自动重连并重试，默认最多 3 次。
- 所有命令按队列串行发送，避免并发写同一个 Socket。
- 支持部分发送，直到完整报文发送完成。
- 持续接收设备返回数据，远端关闭时标记连接失效。
- 禁用或退出时安全关闭连接。
- 所有原事件名、业务调用和十六进制报文保持不变。

### 6.2 修复一键操作

- 一键操作执行每个目标前，先用 `SetIsOnWithoutNotify(false)` 重置，再设置为 `true`，保证每次都触发命令。
- 设备批量操作与灯光批量操作各只允许一个协程，新的批量任务会取消同类旧任务，避免叠加。
- 一键按钮在完成后自动恢复，允许再次执行。
- 设备保留原来的 2.6 秒间隔，避免大批设备同时上电。
- 灯光命令缩短为 0.8 秒触发间隔，底层 TCP 队列负责串行发送。

### 6.3 约束 UDP 实例

- 多个 `UDPClient` 仍可保留以兼容旧 prefab，但只有当前活动实例允许初始化和发送。
- 首个启用的场景实例作为稳定传输所有者；动态创建的 Relay prefab 不再抢占并关闭健康 Socket。
- 活动实例失效时自动选择仍启用的后备实例，并恢复最近一次 UDP 目标配置。
- 重新初始化前先释放旧传输资源。
- 接收线程改为后台线程，通过关闭 Socket 退出，不再使用 `Thread.Abort`。
- 增加未初始化、地址错误、发送异常日志。
- `UDPClient2` 同步实施安全关闭和活动实例限制。

### 6.4 加固全局事件中心

- 重复注册同一回调时先移除旧回调，避免监听累积。
- 移除不存在的监听不再抛异常。
- 没有订阅者时广播不再抛异常。
- 每个订阅者独立 `try/catch`，一个模块报错不会阻止其他设备收到一键控制事件。

## 7. 网络唤醒问题分析

### 7.1 已排除 APK 权限缺失

从原 APK 实际权限中确认已有：

- `android.permission.INTERNET`
- `android.permission.ACCESS_NETWORK_STATE`

发送 UDP 不需要位置权限；本问题不是缺少 `INTERNET` 权限造成的。

### 7.2 为什么有线服务端可以，Wi-Fi 平板不可以

Wake-on-LAN 依赖魔术包到达关机设备所在的二层广播域。当前现象可以推导出：

1. 目标设备 BIOS/NIC 的 WOL 大概率已经正确启用，因为有线服务端能唤醒。
2. 有线中控主机与目标设备之间的广播路径可用。
3. Wi-Fi 到有线 LAN 的广播路径被 AP、访客网络、无线隔离、VLAN 或广播抑制策略阻断的概率很高。

旧代码只执行：

```text
255.255.255.255:50000，发送一次
```

很多 AP 不会把这种有限广播从无线侧桥接到有线侧；这不是重发一次就一定能解决的。

### 7.3 已实施的 WOL 改进

- 修复 MAC 正则允许冒号但解析函数只支持连字符的问题。
- 支持 `AA-BB-CC-DD-EE-FF`、`AA:BB:CC:DD:EE:FF`、连续 MAC 等格式。
- 显式启用 UDP Broadcast。
- 同时发送到：
  - `255.255.255.255`
  - 自动根据平板 IPv4 地址和子网掩码计算的定向广播，例如 `192.168.86.255`
  - Inspector 可手工填写的定向广播地址
- 同时覆盖 UDP 端口 `9`、`7`、`50000`。
- 每个目标默认重复发送 3 次。
- 修复通过 `new MonoBehaviour()` 获取单例的不合法用法。

### 7.4 代码无法绕过的网络限制

如果 AP 明确禁止 Wi-Fi 客户端向有线网发送广播，Android 应用无法通过普通 UDP API绕过。此时必须二选一：

1. 调整 AP/交换机配置：平板和设备置于同一 VLAN，关闭客户端隔离/访客隔离，允许无线到有线广播。
2. 保留有线 WOL 服务端作为网关，由平板发送普通单播指令给服务端，再由服务端发送魔术包。

当前改进会显著增加普通桥接 Wi-Fi 下的直发成功率，但现场是否允许广播必须通过抓包验证。

## 8. WOL 现场验证步骤

1. 确认平板 Wi-Fi IP、掩码和目标电脑有线 IP，例如都在 `192.168.86.0/24`。
2. 确认平板没有连接访客 Wi-Fi，AP 未开启 Client Isolation/AP Isolation。
3. 在同一有线网电脑上运行 Wireshark，过滤：

   ```text
   udp.port == 7 || udp.port == 9 || udp.port == 50000
   ```

4. 平板点击网络唤醒。
5. 若抓不到包：检查 AP 的无线到有线广播转发、VLAN、广播抑制。
6. 若能抓到魔术包但设备不醒：检查目标设备 BIOS、网卡高级选项、关机供电、Windows 快速启动和交换机端口节能。
7. 连续测试冷关机、正常关机、休眠三种状态，每种至少 20 次。

## 10. 建议的现场回归测试

### 10.1 单设备控制

- 每个设备连续执行开/关各 30 次。
- 每次操作间隔 1～3 秒随机变化。
- 记录 UI 点击时间、日志中的连接/发送时间、设备实际动作时间。
- 测试中途关闭一个继电器网络 10 秒，再恢复，验证自动重连。

### 10.2 一键控制

- 一键全开、一键全关各执行 20 轮。
- 专门验证“UI 已显示开，但人工把设备关掉”后再次一键全开，必须重新下发。
- 操作进行中点击相反的一键命令，确认旧批次取消、没有命令交叉。
- 记录每轮漏执行设备数量。

### 10.3 长时间运行

- 连续运行 24～72 小时。
- 每小时切换视频/软件控制面板并执行设备开关。
- 观察 Android 内存、线程数、Socket 数、Wi-Fi 重连后的恢复情况。

### 10.4 建议验收指标

- TCP 指令进入发送队列成功率：100%。
- 在网络可达、设备正常情况下，单设备动作成功率目标：≥99%。
- 一键全开/全关每轮无漏项。
- Wi-Fi 短时断开并恢复后，不重启应用即可继续控制。

## 13. 后续补充整改

- TCP 连接状态增加端口维度，修复同 IP 切换端口仍复用旧连接的问题。
- `MyUDPClient`、`UDPClienthongwai`、`UDPClientServer` 和串口控制器全部改为关闭 Socket/串口后安全退出后台线程。
- Socket.IO 重连等待由错误的 5 毫秒修正为 5 秒，Ping 超时由毫秒/秒混用修正为真实秒数，并移除 `Thread.Abort`。
- 安卓设备与软件配置读取改为 Unity 协程异步读取，不再在主线程空循环等待 `UnityWebRequest`。
- 安卓 StreamingAssets 首次复制改用 AssetManager 直接读取，不再忙等网络请求。
- `GameResources` 改为普通服务类，修复通过 `new MonoBehaviour()` 创建实例的非法用法。
- 新增现场诊断日志，自动记录 TCP 连接、命令入队/发送/重试/回包、一键批次进度及 WOL 实际发送目标。日志位于安卓应用持久化目录的 `ControlDiagnostics/control-*.tsv`。

## 14. 当前结论

客户反馈不是单一的“Wi-Fi 信号不好”，旧代码中确实存在多个会稳定复现命令丢失、连接互相覆盖、Toggle 不重复触发和 UDP 资源累积的问题。第一阶段已针对这些确定性缺陷完成兼容修复。

网络唤醒的应用代码已经增强，但“无线侧广播是否能进入有线 LAN”最终由 AP/VLAN 策略决定。现场抓包是区分代码问题与网络设备策略的必要步骤。
